3. BUGG SOM HITTADES VID SLUTTEST — FIXAD (commit 88eb51f)
-------------------------------------------------------------------------------

SYMPTOM: Användaren (icke-referensförälder) gjorde en "förfrågan om
datumändring" i live-appen. Fick "Kunde inte skicka förslaget. Försök igen."
Browser-konsol: POST .../applyScheduleChangeDirect 400 (Bad Request).

DETTA ÄR EN PRE-EXISTERANDE KLIENTBUGG. Inte orsakad av regionväxlingen eller
disk-cachen — regionväxlingen fick bara användaren att testa notis-flödet
(som icke-referensförälder) för första gången, vilket avslöjade den.

ROT: app/page.tsx:567
  const otherParentId = parents.find((p) => p.id !== balance?.referenceParentId)?.id ?? parents[1].id;

`otherParentId` = "föräldern som inte är ställningens referensförälder" — en
FAST person, oberoende av vem som är inloggad. referenceParentId = den som
satte upp boendecykeln.

Flöde före fix (page.tsx onProposeShift / onProposeShiftBatch):
  mode: scheduleChangeModeFor(team, otherParentId)
  - Om inloggad user ÄR referensföräldern: otherParentId = den andre. OK.
  - Om inloggad user INTE är referensföräldern: otherParentId = HEN SJÄLV.
    -> klienten läser sitt EGET läge ("notis") -> anropar
       applyScheduleChangeDirect.
    -> servern (functions/src/index.ts applyScheduleChangeDirect) kollar
       KORREKT motpartens läge via parentIds.find(id => id !== uid) =
       default "request" -> throw HttpsError("failed-precondition", ...) -> 400.

Klient och server var oense om VEM motparten är.

FIX (page.tsx:576):
  const counterpartId =
    parents.find((p) => p.id !== user?.uid && p.id !== PENDING_PARTNER_ID)?.id ?? otherParentId;
  -> används på page.tsx:864 och :874 istället för otherParentId.
  -> otherParentId LÄMNAT ORÖRT för BalanceCard (page.tsx:755), som verkligen
     vill ha icke-referensföräldern (ställningen är signerad mot
     referensföräldern).

Deployad live (hosting, HEAD 88eb51f).

8. DEPLOYMENT-ANTECKNINGAR FÖR FRAMTIDEN
-------------------------------------------------------------------------------
- Regionändring = Firebase behandlar det som en FLYTT (skapa ny + radera
  gammal). Non-interactive `firebase deploy` AVBRYTER hellre än att göra
  halvt. Ska en funktions region ändras igen: radera den gamla regionens
  kopia FÖRST (`firebase functions:delete <namn> --region <gammal>`), sen
  deploya.
- `--force` på `firebase deploy --only functions` krävs för att auto-
  konfigurera Artifact Registry-cleanup-policy i en ny region (annars exit 1
  fast funktionerna deployas korrekt).
- onSchedule-funktioner kan INTE ligga i europe-north1 (Cloud Scheduler
  saknas där). europe-west1 har Scheduler om samlokalisering med Europa
  önskas; annars us-central1.
- GitHub Actions-deployen (.github/workflows/deploy.yml) fungerar fortsatt;
  service account github-actions-deploy@varannan-familj.iam.gserviceaccount.com.
- Denna sessions deploys gjordes lokalt; README säger att GitHub Actions är
  den normala vägen.
